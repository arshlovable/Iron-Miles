3. AUTH FLOW AUDIT
================================================================================

FILES INSPECTED:

  - frontend/app/auth.tsx
  - frontend/app/_layout.tsx (AuthGate)
  - frontend/src/lib/supabase.ts

--------------------------------------------------------------------------------
3.1 Flow Summary
--------------------------------------------------------------------------------

New user:
  1. Onboarding (7 screens) → answers stored in OnboardingContext + AsyncStorage flag
  2. Auth screen (signup) → Supabase signUp
  3. If immediate session: ensureProfile + flushToProfile → AuthGate → /(tabs)
  4. If email confirmation required: confirmation screen shown

Returning user:
  1. Onboarding skipped (AsyncStorage flag set)
  2. Auth screen (signin) → AuthGate → /(tabs)

App restart:
  - supabase.auth.getSession() restores session from AsyncStorage (native)
  - onAuthStateChange keeps session in sync
  - AuthGate routes authenticated users to /(tabs)

Logout:
  - signOut() clears Supabase session + local profile state
  - AuthGate routes to /auth (onboarding flag remains set — user skips onboarding)

--------------------------------------------------------------------------------
3.2 Verification Matrix
--------------------------------------------------------------------------------

-----------------------------------|--------|----------------------------------

Existing users can sign in         | PASS   | signInWithPassword

Users can logout                   | PASS   | signOut implemented

--------------------------------------------------------------------------------
3.3 Known Gap (Low Risk for V1)
--------------------------------------------------------------------------------

If Supabase email confirmation is ENABLED:
  - signUp returns status: 'confirmation_required'
  - flushToProfile is NOT called at signup time
  - Onboarding answers (goal, equipment, time, driver type) are lost
  - User lands in app without personalized profile fields

Mitigation for launch: Keep email confirmation disabled in Supabase Auth settings.
Future fix: Re-flush onboarding data when session arrives via onAuthStateChange,
or persist onboarding answers until first successful profile update.

Removed verbose console.log from:

  - AuthContext — was logging emails, UIDs, session state on every event
  - auth.tsx — was logging submit mode and email

Retained console.warn for actual errors (ensureProfile, refreshProfile).

--------------------------------------------------------------------------------
5.1 Manual Supabase Dashboard Checklist
--------------------------------------------------------------------------------

For each table, verify RLS is ENABLED and policies exist:

TABLE: exercises
  [ ] SELECT allowed for anon and/or authenticated (public catalog)
  Without this: workout generator returns empty exercise pool

  [ ] SELECT allowed for anon and/or authenticated (public catalog)
  Without this: fuel food picker is empty

  [ ] INSERT: auth.uid() = id  (signup upsert)
  [ ] UPDATE: auth.uid() = id  (onboarding flush, settings)

  [ ] SELECT: auth.uid() = user_id
  [ ] INSERT: auth.uid() = user_id
  [ ] UPDATE: auth.uid() = user_id (or service role only via edge fn)

  [ ] SELECT: via parent generated_workouts ownership OR own policy
  [ ] INSERT: authenticated user who owns parent workout

TABLE: workout_sessions
  [ ] SELECT: auth.uid() = user_id
  [ ] INSERT/UPDATE: service role (edge functions) OR auth.uid() = user_id

  [ ] SELECT: auth.uid() = user_id

  [ ] SELECT: auth.uid() = user_id

--------------------------------------------------------------------------------

5. Returns generated_workout + exercises array
6. Frontend navigates to generate-workout result screen / workout-ready

Inputs validated:
  - user_id required (throws if not signed in)
  - equipment defaults to ['bodyweight'] if empty
  - difficulty normalized to easy | medium | hard
  - Goal mapping: lose_weight → burn_calories, move_better → mobility

--------------------------------------------------------------------------------
6.2 Filtering Logic (Edge Function)
--------------------------------------------------------------------------------

  - Target area / body focus normalization
  - Equipment filtering (bodyweight, bands, dumbbells, full)
  - Duration → exercise count
  - Difficulty → sets/reps/rest adjustments
  - Core/back relief fast_lane bypass
  - Goal tags and workout_style matching
  - is_active filter on exercises
  - Fallback if pool too small (relaxes filters)

6.3 Save Flow
--------------------------------------------------------------------------------
